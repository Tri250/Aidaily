# 16 · 2.0 功能设计

面向维护者与仓库 agent 的 2.0 体验规划：现状盘点、痛点、分层功能设计、里程碑与落地要求。
本文档是设计约定，不是使用说明；用户文档仍是 `docs/00` 到 `docs/15` 和各机型清单。

状态标记：**已落地** = 代码与回归已进「未发布」段；**设计中** = 方案已定，等实现；**待真机** = 设计已定，必须真机核对后才能合入（硬规则：自检通过≠适配完成）。

## 1. 现状盘点（模块边界）

| 层 | 模块 | 能力 | 成熟度 |
|---|---|---|---|
| 引擎 | `tool/fast.py`（读屏点击） | 开关识别、`plan_switches()` 拨动计划、`off()` 带回读、落点校验、推广位防护、dry 预览 | 高，边界清晰 |
| 引擎 | `tool/chan_fast.py` + `channel_policy.py` | 营销渠道扫描/关闭/还原，关键词+厂商 ID 分类 | 高 |
| 引擎 | `tool/run.py`（总入口） | 17 条子命令，`COMMANDS` 表分发，`status-json` 已是机器可读出口 | 高 |
| 适配 | `tool/adapt.py` + `recipes/` 35 份机型脚本 | 四段适配流水线，`@step` 段落框架 | 高，但覆盖追不上机型 |
| 客户端 | `gui/app.py`（pywebview）+ `gui/web/index.html` | 五步向导、Job/Task 调度、暂停/停止、诊断上报 | 中，扩展点在 Job 组装 |
| 质量 | `tests/`（无真机回归） | 全部引擎行为用假设备时间轴对拍 | 高，新能力必须同样对拍 |

耦合热点：`off()` 是引擎最敏感函数（#480/#486/#555 的修复都在这里），任何拨动方向相关的新能力都必须复用它的计划语义，不得另写一套。

## 2. 痛点（有据可查）

| 编号 | 痛点 | 证据 |
|---|---|---|
| P1 | 点「开始」前不知道会改哪些；App 内开关关掉后只能照清单手动还原 | `docs/05-还原.md`、还原弹窗三按钮的限制 |
| P2 | 干净不持久：系统升级把设置打回原形、msa 被重新拉起，没有复查机制 | `docs/归档/CHANGELOG-0.3.0及更早.md` 挂起复活记录、#192 |
| P3 | 上手门槛：开发者模式/USB 调试是最大流失点；读屏被 GKD 等占用是最高频 issue | `docs/00`、`docs/09` 判据表第一行、#323 系列 |
| P4 | 覆盖不足：35 份脚本 vs 海量机型；参考脚本安全模式命中率低；繁体刚补、英文界面机型不支持 | README 机型表「无专用脚本」行 |
| P5 | 效果不可感：backups/ 存了数据，没有历史视图、没有量化 | 现状 |

## 3. 设计原则

1. 对齐 AGENTS.md 硬规则：只读优先；`pm suspend` 必经用户同意；保护类开关只开不关；不 root、不碰 system。
2. 增量不重构：新能力挂在现有模块边界上（`off()` 语义、`COMMANDS` 表、Job/Task、backups/ 目录），不另起炉灶。
3. 每个功能可单独回退：CLI 加命令、GUI 加入口，互不阻塞发布。
4. 没有真机不能宣称完成：引擎行为先过无真机回归，再按 `docs/1x` 实测惯例补真机记录。

## 4. 功能设计

### 2.1 执行前预览【已落地】

解决 P1 的前半段：开始之前知道要改什么。

- 形态：
  - `run.py -s S recipe --dry [段名…]`：按机型脚本走一遍页面，逐段报「将关 N 项：…；将打开（保护类）M 项；K 个被上级开关禁用」；不点击、不回读、不写 run-log。
  - `fast.py -s S dry`：预览当前页。
- 实现（已进代码）：
  - `Phone.dry / dry_plan` 字段；`off()` 在 `wait.until` 后分流进 `_preview()`；
  - `_preview()` 与正式执行共用同一个 `plan_page()` 闭包——`plan_switches` 的 targets/kept/disabled 语义同源，预览列出的就是会点的开关；
  - 翻页后同一行可能仍在视野里：按标题去重，同一开关只报一次；
  - `execute("run")` 识别 `--dry`（与 `--ref` 同路），结尾打印「预览完成：将改动 N 项（关 X、打开 Y）」；
  - `run.py --help`、README 命令表、AGENTS.md §3/§4 已同步。
- 验收（已过）：`tests/test_dry_run_preview.py` 8 项——计划内容写死断言、零点击、对照正式执行会点、灰开关只说明不计划、翻页去重、CLI 传参与退出码。
- 待办：GUI 在「执行」步前插入预览 Job 任务（`Job` 组装时在 recipe 任务前跑一次 `--dry` 并渲染摘要），前端暂未接。

### 2.2 干净度估算分【已落地】

解决 P5 的量化：给用户一个能感知的分数，执行前后对比。

- 形态：`run.py -s S score`（只读），输出三类扣分与总分：
  - 营销通知候选（chan-scan 的候选数）：-2/个，封顶 -40；明确提示「候选不全是广告」；
  - 未挂起的广告组件（`ad_packages` 且 installed 且未 suspended）：-15/个；
  - 未关闭的快应用（`quickapps`，排除 keep 项）：-10/个；
  - 扫描失败该类不计分、不冒扣分；
  - 结尾固定声明「App 内开关不参与计分，跑完 recipe 分数不变」，防止误判 recipe 没生效。
- 实现位置：`run.py` 的 `SCORE_WEIGHTS` 常量 + `cmd_score()`；起子进程扫描，故按惯例列入 `run_cli_cases.py` 的 `HOST_SIDE`，转发语义由 `test_run_commands.py` 替身化覆盖。
- 验收（已过）：`tests/test_score_command.py` 4 项——分类计数与扣分、全清 100 分、扫描失败兜底、封顶。
- 待办：GUI 检测页展示分数与前后对比（数据走现有 `status-json` 同款只读通道）。

### 2.3 一键还原执行【设计中，待真机】

解决 P1 的后半段：App 内开关从「只能手动」变「一键」。

- 形态：`run.py -s S recipe --restore [段名…]`；GUI 还原弹窗加「一键还原（含 App 内开关）」按钮，与现有 quickapp on / unsuspend / chan-on 并列。
- 引擎方案：
  - `Phone` 增加与 `off()` 同构的 `on()`：复用同一 `plan_page()` 闭包与翻页循环，仅拨动方向翻转——普通开关拨回「开」；保护类开关本来就是开，保持不动；
  - 机型脚本不需要重写：`@step` 框架在 restore 模式下复用同一批入口路径与 `only()` 名单，只换拨动方向；
  - 开启时可能弹确认框：先走现有 `confirm()` 机制，识别不了的页面按「未完成步骤」如实报告，绝不盲点「允许」（硬规则第 6 条）。
- 边界与风险：
  - 开启态的页面行为与关闭态不同（有的页开启需二次确认、有的开关开启即跳页），每个机型脚本还原一遍必须真机核对；
  - 广告服务复活机制未定位（归档记录），还原后如实报告状态，不宣称「恢复原状」；
  - 挂起还原走现有 `unsuspend`，渠道还原走 `chan-on`，本功能只管 App 内开关。
- 验收：真机九段「先关后还原」各跑一遍；还原后 `check`/`scan` 显示与首次 backup 快照一致；新增对拍用例先于实现。

### 2.4 变更历史（results.json）【设计中】

解决 P5 的数据基础，也是 2.5/2.6 的前提。

- 数据层：每轮执行收尾在 `backups/<型号>-<时间>/` 里写 `results.json`（与现有快照同目录，不新增隐私面）：
  - `model / os / build / ts` 设备与时间；
  - `changed`（页面+开关）、`missed`、`chan_off`（渠道 ID 清单）、`suspended`（包清单）、`quickapp`；
  - 预览数据不进 results.json（预览不是变更）。
- 写入点：`run.py finish` 汇总；GUI 的 Job 结束路径回传同一格式。只存开关标题与状态，不存序列号、账号、截图。
- 展示：GUI「历史」面板读 backups/ 目录聚合成列表（日期、分数、关了几项、哪些渠道），点开看单项 diff；CLI 出 `run.py history` 只读命令同源。

### 2.5 漂移复查（recheck）【设计中，依赖 2.4】

解决 P2：系统升级后「广告回来了」不再靠感觉。

- 形态：`run.py -s S recheck`：读最近一次 `results.json`，逐项只读核对——开关还在不在（`scan` 语义）、包还挂不挂（`suspended`）、渠道还关不关（`chan_fast` 回读）——输出「被改回去的项」清单；`recheck --reapply` 对差异项重跑对应段落。
- 边界：
  - 系统版本与基线不一致时先提示机型脚本版本匹配（现有 BUILD 录制版本机制），不直接开跑；
  - 找不到基线（换目录/没跑过）就说没有基线，不拿 backup 的「改动前」快照冒充「改动后」基线。

### 2.6 复查提醒【设计中，依赖 2.4】

- GUI 连接成功时读 `results.json`：系统版本变了、或距上次执行超过 30 天，就在连接页显示「建议先复查」入口。
- 不做后台常驻、不做定时任务：只在连接时计算一次，保持工具「不挂后台」的气质。

### 2.7 上手向导与读屏冲突自愈【设计中】

解决 P3。

- 上手向导：GUI 检测不到设备时，按 `ro.product.brand`（或用户选择）展示品牌专属步骤，素材取自 `docs/00`；补无线调试引导（现有 docs 已写，向导内嵌）。
- 冲突自愈：`ui-check` 扩展为只读检查 `settings get secure enabled_accessibility_services` 与 `dumpsys accessibility`，把 GKD、自动记账这类「占用 UiAutomation 的服务」按应用名点出来，引导用户暂停后点「重新检查」。
- 边界（对齐 `docs/11`）：不自动停用任何辅助服务、不杀进程、不重启手机；只点名、只给建议。报错文案按 `docs/09` 判据分类，命中判据的直接给处置建议。

### 2.8 词表 i18n【设计中】

解决 P4 的语言面：海外界面机型（README 已有俄语 Redmi Note 13 案例）引擎完全找不到入口。

- 方案：把 `fast.py` 的判据词（`AD_WORDS`/`TRACK_WORDS`/`NEG_PREFIX`）、`EXPECT_TAIL` 词表、`fast.py` 顶部 ALLOW/KW/SKIP 外置为 `tool/words/<locale>.py` 数据文件，运行时按 `ro.product.locale` 选择；先补 `zh-CN`（现状）、`zh-TW`（沿用现有映射）、`en`。
- 边界：词表是行为核心，判定必须先对拍（同一页面 XML 换词表跑两边）；机型脚本标题仍按各机型实际界面语言写，不受全局词表影响。

### 2.9 反馈前自查【设计中】

降低无效 issue（P3/P4 的连带）：反馈前先按 `docs/09` 判据表本地匹配已知问题，GUI 反馈框先展示「已知同类问题」，未命中才给 issue 链接；新增 `run.py -s S diagnose` 只读聚合（ui-check + check + 版本 + 最近 FAILED_STEPS）自动附进上报页。

## 5. 明确不做

- 不做后台常驻/定时自动执行（保持手动触发 + 连接时提醒）；
- 不做 root 级清理、不改 system 分区（硬规则第 4 条）;
- 不自动停用用户的辅助服务、不替用户同意任何协议（硬规则第 6 条、`docs/11` 边界）；
- 不做批量多设备并行（需求不明确前不引入队列复杂度）。

## 7. 落地要求（每个功能）

1. 引擎行为改动先写 ADR（尤其碰 `off()` 语义的）；
2. 无真机回归先行：新增行为必须有对拍用例，断言写死、不重算实现；
3. 新命令同步四处：`run.py`/`fast.py` 的 `__doc__`、README 命令表、AGENTS.md、CHANGELOG「未发布」；
4. 真机核对按 `docs/1x` 实测记录惯例补档，问题号标注清楚（#NNN）；
5. 涉及起子进程/依赖本机 adb 的命令，按惯例列入 `tests/run_cli_cases.py` 的 `HOST_SIDE` 并补替身化断言。
