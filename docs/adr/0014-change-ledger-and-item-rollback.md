# 变更账本：一次执行改了什么按条目落盘，条目自带单条还原的数据

基线 `8ddcd67`（v0.3.2）。

现状是"整类还原"：还原中心只有三个大按钮（恢复快应用 / 恢复挂起的广告组件 /
重新打开关掉的营销通知），一按就是全量。用户只想恢复某一个 App 的营销通知，
或者只想把某一个广告组件拉起来，做不到。同时完成页只列"每步 rc"，到底改了
哪些渠道、哪些包，要到备份目录里翻 channels.tsv，再对照引擎日志。

## Decision

**新增 `tool/ledger.py`：执行结束把改动写成条目账本（JSON），每条带
`undo` 数据；还原时只认条目里写明白名单方法。**

- 条目两类：`channel`（还原 = `chan_fast.py on <单行清单>`，行数据原样保留在
  条目里）；`package`（还原 = `run.py unsuspend <包名>`）。
- 条目的"改成了"只写实际观察到的结论：该步 rc==0 才写"已关 / 已挂起"，
  否则写"未确认"。rc 非 0 时哪一条没成并不知晓，不猜。
- 落点 `<数据目录>/ledgers/<时间>-<批次>.json`，文件 0600、目录随数据目录；
  不上传。给前端前经 `scrub()` 把序列号替换掉——导出脱敏清单因此只是
  "读账本 + 复制"，不需要第二条脱敏路径。
- `undo_plan()` 只认 `chan_on` / `unsuspend` 两个方法名，其余拒绝
  （`LedgerError`）。账本文件本身是本地数据，但还原命令的参数只从
  白名单形状里取，坏文件给不出可执行的意外命令。
- 查询接口 `Api.ledger(serial)`：串号精确匹配；执行中拒绝（与 restore
  同一守卫）。`latest()` 不接受空串号回退匹配——沿用 backups.latest("") 的教训。
- 写入在 `_work()` 收尾、`running=False` 之前，异常只记一行日志：
  账本是留痕，故障不能挡收尾，更不能让用户以为执行失败。

## Considered Options

- **账本记在内存 / Job 里**（不落盘）：客户端重启就没了，还原中心仍然只有
  整类还原，2.0 的"变更清单与回滚"没有地基。
- **逐条目记引擎日志行再解析**：引擎各段日志格式不一，解析是第二份真相，
  坏一处还原就错。改用任务清单 + rc 这一已有结构，条目级别够用。
- **挂起条目按包解析引擎输出**：`cmd_suspend` 失败时逐包行格式不保证稳定，
  解析会把"部分成功"误写成全成。保持 rc 级结论。
- **清单文件即账本**（继续只靠 channels.tsv）：它没有 after 状态、没有
  快应用 / 挂起，也没有批次，还原中心要自己拼三种来源。

## Consequences

- 完成页新增"这次改了什么"卡片与"导出脱敏清单"；还原中心在三个大按钮之上
  增加勾选逐条还原。执行中的守卫与文案沿用 restore 的。
- 备份目录（含 channels.tsv）顺带收紧到 0700——同一份隐私数据，账本收紧了，
  旁边明文目录不能不收（M-12 的第一步；整体加密等依赖决策，不在本 ADR）。
- 断连文案改为指向完成页的「继续未完成的步骤」（FR-09/10 的前端入口，
  映射关系 `retryPlan()` 在 `gui/web/index.html`，已成功步骤不重跑）。
- 看板 / 指标（M-01、R-09）从账本文件聚合即可，2.1.0 再做，不在本版埋上传。
