## 阅读指引：结论先行

**一句话结论**：v0.3.2 不是「功能迭代版」，而是 Tri250 把上游 `rddmwmddr/android-ad-cleaner` 完整历史导入自有仓库后的**首个可发布基线**——它证明的是「发版闭环跑通了」，不是「产品能力升级了」。真正的瓶颈不在代码质量，而在**产品形态**：治理能力被写死在 37 份 Python 机型脚本里，一次执行只解决「这一刻、这一台、这一版系统」的广告，缺少变化感知、结果解释与规则回流。

**2.0 的建议主张**：从「机型脚本驱动的一次性清理工具」升级为「**规则数据驱动、可自适应、可运营的手机广告治理平台**」，用三条主线收口——规则数据化（Rule-as-Data）、治理生命周期化（Continuous Care）、交互极简化（5 步 → 3 步）。

**最该先做的三件事**：① 规则包与签名校验底座（M-02）；② 三步一键治理 + 断点续跑（M-04）；③ 变更清单与单条回滚（M-05）。这三件不依赖云端、不触碰「不 root / 不卸载 / 不改 system」硬边界，却能把「有的没关」「误关了怎么办」「失败要整轮重跑」三个最高频痛点一次性解决。

> **证据口径说明**：本文所有现状数字均来自仓库源码、Git 历史与 GitHub API（快照时间 2026-11-04），以 `路径:行号` 或 commit 短哈希标注；所有 2.0 目标值一律标注「目标值·待基线确认」——当前仓库**没有任何埋点与指标看板**（`gui/app.py` 无埋点代码，`docs/` 无指标口径文件），不具备设定定量目标的基线，先埋点再定阈值。

**`3f5089d` 修复的三处，恰好暴露了当前架构的脆弱点**（`tests/test_gui_loop_guards.py` 的注释写得很直白）：

1. 执行中侧栏「还原改动」可点 → `chan_fast on` / `unsuspend` 会与正在跑的任务**并发抢同一台手机**；
2. 手机断开时 `restore("channels")` 拿到空型号，`Backups.latest("")` 的 `startswith("")` 会**匹配任意型号备份目录**——差点把别的手机的营销通知清单还原到这台机上；
3. 断连文案承诺「重新连接后点『重试』」，但完成页**根本没有这个按钮**（本次补了 `retry()` 并清空过期的渠道扫描缓存）。

**`8ddcd67` 则暴露了发布链路的人工依赖**：官网 `index.html` 的 `REL` 常量硬编码版本号、下载基址、百度网盘链接、四个文件名、大小与 SHA-256（`index.html:415-435`），必须靠一个测试 `test_promo_page_download_base_matches_app_version` 守护一致性；Mac 版甚至只改了文件名字符串，实际仍是 `0.3.1` 的产物名占位。这不是「自动化发版」，是「靠测试提醒人别漏改」。

## 1.3 产品定位与四条使用路径

产品解决的是：**国产安卓手机系统里的广告、热搜、资讯推荐与营销推送**，通过 adb 连接手机后拨动系统自带开关，不 root、不解锁、不刷机（`README.md` 开头与「不做的事」）。

| 路径 | 入口 | 前置条件 | 现状 |
|---|---|---|---|
| 一 · AI 智能体替你跑 | `AGENTS.md` + 外部 AI 工具（WorkBuddy / Claude Code / Codex / Trae / Cursor） | 电脑 + 会执行命令的 AI | 文档规范齐全，但**能力在外部工具里，仓库内无 AI 实现** |
| 二 · 聊天 AI 带你点 | `prompts/聊天AI提示词.md`（仅 1 个文件） | 手机 + DeepSeek / 豆包 / ChatGPT | 纯提示词，无产品化封装 |
| 三 · 照清单手动关 | `docs/清单/` 8 份品牌清单 | 只要手机 | 覆盖 8 个品牌，靠人工比对着点 |
| 四 · 桌面客户端 | `gui/`（pywebview + PyInstaller） | Mac / Windows + 数据线 | **主交付形态**，v0.3.2 只发布 Windows 两个包 |

v0.3.2 Release 资产仅 3 个：`AndroidAdCleaner-0.3.2-windows-portable.zip`（45,199,881 B）、`AndroidAdCleaner-0.3.2-windows-setup.exe`（30,319,443 B）、`SHA256SUMS.txt`（219 B）。**Mac / Linux 安装包在本 Release 中缺失**，但官网 `index.html` 仍列出 4 个文件（含两个 Mac dmg 与旧 SHA）——这是一个必须写进 2.0 范围的一致性缺陷。

## 1.4 不可逾越的硬边界（2.0 必须继承）

来自 `README.md`「不做的事」、`.out-of-scope/app-splash-ads.md`、`docs/06-常见问题.md`：

- **不 root、不解锁 BL、不刷机、不改 system 分区、不装模块**；
- **不卸载、不停用系统应用**（不用 `pm uninstall` / `pm disable-user`），广告组件只用 `pm suspend` 且必须机主点头、可一条命令还原；
- **不替用户同意任何 App 用户协议**，遇协议页点「取消 / 以后再说」；
- **不截账号页和手机号页**，不采集通知正文、应用列表；
- **不处理 App 自身开屏广告**（`.out-of-scope/app-splash-ads.md` 明确论证：需 root / 拦网 / hook / 无障碍自动跳过，均越界或属其他工具职责）；
- **仅支持 adb 连接的安卓设备**，不支持原生鸿蒙 HDC；
- 执行期间用户不能碰手机，需保持亮屏、解锁、插线。

> 这七条是产品的**信任资产**。2.0 任何「智能化 / 平台化 / 云端化」设想，都必须先过这七条的合规闸门；本文所有方案均以此为前提设计。

## 2.2 CLI 命令清单（15 条，`tool/run.py:833-864`）

`COMMANDS` 注册 13 条：`ui-check`、`check`、`backup`、`recipe`、`chan-scan`、`chan-off`、`chan-on`、`suspend`、`unsuspend`、`quickapp`、`finish`、`status-json`、`dev-off`；另有不进字典的 `devices`（无需序列号）与 `adapt`（转 `tool/adapt.py`）。每条命令一个 handler，退出码 0/1，转发类命令透传子进程码（`CONTEXT.md:11-15`，ADR-0005）。

`adapt`（0.3.0 新增，`tool/adapt.py`）已是**规则流水线的雏形**：`explore` 探路 → `gen` 按人工勾选生成草稿 → `check` 安全模式自检（`render_draft` / `check_draft` / `print_report`）。这是 2.0「规则数据化」最值得复用的既有资产，而不是另起炉灶。

## 2.3 客户端：五步流程与窗口桥

前端是**单文件** `gui/web/index.html`（46,719 B，内联 CSS + 原生 JS），通过 `file://` 直读（规避早期 HTTP 超时问题）。状态机由 `showConnect → showDetect → showChoose → showRun → showDone` 五个函数构成（`index.html:162/234/275/364/412`），侧栏另有 `openFeedback / openReport / openRestore / openSettings / openChecklist`。

`Api` 暴露约 22 个窗口桥方法（ADR-0011 明确「22 个方法名与签名不变」），包括 `env / latest_version / devices / status / chan_scan / ui_check / start / poll / stop / pause / resume / dev_off / restore / diagnostics / report_payload / send_report / copy_text / open_path / open_url / adb_info / set_adb_path / download_adb`。**前后端契约稳定、内部可拆分**——这是 2.0 前端组件化改造可以直接复用的约束。

## 2.4 引擎中真正值钱的设计（`CONTEXT.md` + `fast.py`）

| 设计 | 含义 | 2.0 价值 |
|---|---|---|
| **回读** | 拨完开关重新读控件状态，只看「点到了」不算数 | 变更清单的可信数据源 |
| **拨动计划 `plan_switches()`** | `targets / checked / kept / disabled` 四态预算，计划本身不点击 | 可直接映射为「执行计划预览」 |
| **安全模式 `--ref`** | 只关参考脚本点名的开关，找不到就跳过，零猜测性点击 | 规则包灰度与未知机型降级的现成机制 |
| **录制版本 `BUILD`** | 脚本头部记录按哪版系统录的，跨型号借用时前缀比对，不符自动降级安全模式 | 规则包版本匹配的原型 |
| **落点 / 推广位防误点** | `start(expect=…)` 校验停在哪个页；`dismiss()` 点完发现前台换 App 就退回并记下不再点 | 智能化必须保留的安全带 |
| **事件行 / 载荷行** | 引擎另报机器行，客户端剥离；事件改状态、载荷只进上报 | 埋点通道已经存在，扩展成本低 |

## 2.5 成熟度评价：做得好的地方（2.0 不要推翻）

1. **可逆性设计贯穿始终**：所有动作要么拨系统开关、要么 `pm suspend`、要么关渠道，均有对应还原命令；备份先于改动。
2. **误伤防护极其细致**：受保护渠道、前台服务渠道、灰态开关、同名双列、繁体词表、上级开关禁用、推广位识别——这些是从大量真实 Issue 里磨出来的（`CHANGELOG.md` 0.3.1 一版就修了 20+ 条）。
3. **状态语义严谨**：区分「失败 / 未确认 / 跳过 / 已停止 / APP_DENIED 豁免」（`CONTEXT.md:49, 127`），不把「不知道」写成「没关掉」。
4. **诊断脱敏做到结构级**：页面骨架只含层级、控件类型、百分比位置与标记，**一个页面文字都不带**（`docs/12:37-47`）。
5. **架构有 ADR 守护**：13 份架构决策记录，每次重构留痕，`Api` 拆分、`Job` 状态收敛、`Phone` interface 声明都有对应 ADR。
6. **回归资产厚实**：100 个测试文件，且 0.3.1 已做到「不依赖本机 adb，注入假 adb 路径也能全绿」。

# 第三部分　基线诊断：八个结构性矛盾

> 以下每条都锚定具体证据，不是主观体验评价。等级按「发生概率 × 影响程度」评估（1–5 级，≥15 为高）。

| 编号 | 矛盾 | 证据 | 后果 | 等级 |
|---|---|---|---|---|
| G-01 | **适配规模不经济** | `recipes/` 37 份脚本，每份写死 Activity / 文案 / 坐标（`recipes/oppo-PLG110/recipe.py` 头部 30+ 个 `SETTINGS/OAID/STORE_PROMOTIONS` 常量）；README 机型表 40+ 行中大量 ⚠️ / ❌ / 「待复测」 | 品牌 × 型号 × 系统版本三维组合线性增长，维护成本无上限；「脚本报没找到」是结构性天花板（`docs/06:44-50`） | 高 20 |
| G-02 | **规则是代码，不是数据** | 开关路径写在 `.py` 里；`channel_policy.py` 词表硬编码在源码；新增机型需提 PR 合代码 | 社区贡献门槛高、无法热更新、无法灰度、无法按机型下发；发版才能改一条规则 | 高 20 |
| G-03 | **一次性治理，无生命周期** | `docs/06:23-25` 明说「系统更新后建议重跑」「新装的 App 广告跟踪默认打开，重跑一次」 | 用户装个 App、升个级就回到原点，产品无留存理由 | 高 16 |
| G-04 | **结果不可解释、不可精细回滚** | 引擎输出是人话日志；`restore` 只有 `suspend / quickapp / channels` 三类粗粒度（`gui/app.py:1181-1200`）；备份是本地明文文件（`docs/06:129`） | 「有的没关」对不上具体开关；误关一条只能整类还原或手动找路径 | 高 16 |
| G-05 | **路径长且脆弱** | 电脑 + 数据线 + 开发者模式 + USB 调试 + 五步 + 执行 2–5 分钟不能碰手机（README 各机型实测 121–291 秒） | 新用户流失在「打开开发者模式」；中途中止只能整轮重跑 | 中 14 |
| G-06 | **诊断闭环只到「上报」为止** | 上报 → 维护者人工看 → 手工改脚本（`docs/12`）；`latest_version()` 只提示不下载（`gui/app.py:975`） | 反馈不能自动变成适配能力；旧版不会自动更新，README 反复写「请重新下载」 | 高 15 |
| G-07 | **没有质量数据** | 全仓库无埋点、无指标口径文件、无成功率看板；只有 README 的人工实测表 | 无法回答「哪个机型最该优先适配」「哪条规则最常失败」，优先级靠拍脑袋 | 中 12 |
| G-08 | **平台化底座薄** | 单 HTML 内联 JS/CSS；无 i18n、无深色主题、无组件化；Mac 打包靠本地 `build_mac.sh`（需证书 + 公证）；本 Release 无 Mac/Linux 包；官网 4 个文件名 / SHA 硬编码 | 每加一个功能都在改同一个 46KB 文件；跨平台发布靠人 | 中 12 |

**一句话归因**：工程能力（引擎、测试、ADR、脱敏）已经接近「平台级」，但产品模型仍停在「脚本集合 + 桌面壳」。2.0 的核心不是加功能，是**把能力从代码里解放成可运营的数据与服务**。

# 第四部分　2.0 战略与范围

## 4.1 定位、目标与成功指标

**产品定位**：一个不 root、可逆、可解释、可持续的**手机广告治理平台**——首次使用 3 步完成治理，此后由系统自动感知变化、增量复检，用户随时能看清单、单条撤销。

**北极星指标建议**：「**有效治理保持率**」= 完成首次治理后第 30 天，仍处于目标态的开关数 ÷ 首次成功治理的开关数。它同时约束「一次治得准」和「之后守得住」，比单纯的「执行成功率」更贴合 G-03/G-04。

| 指标 | 定义与口径 | 排除项 | 目标值 |
|---|---|---|---|
| 首次治理完成率 | 完成页「全部成功」的执行次数 ÷ 启动执行次数 | 用户主动「停止」、检测阶段退出、APP_DENIED 豁免 | 目标值·待基线确认 |
| 回读确认率 | 回读确认处于目标态的开关数 ÷ 计划拨动开关数 | 安全模式 `kept`、灰态 `disabled`、扫描排除渠道 | 目标值·待基线确认 |
| **误关率（底线）** | 被判定为「受保护 / 服务类」却发生状态变化的开关数 ÷ 总拨动数 | 无（零容忍） | **0** |
| 规则命中率 | 规则包中成功定位并执行的条目数 ÷ 适用条目数 | 版本不匹配降级为安全模式的段落单列 | 目标值·待基线确认 |
| 机型规则覆盖率 | 有专用规则包且 `BUILD` 匹配的机型数 ÷ 检测到的机型数 | 仅用参考规则 / 安全模式的机型单列 | 目标值·待基线确认 |
| 执行耗时 P95 | 一次执行从 `start` 到 `执行结束` 的耗时 P95 | 暂停等待用户的时间单列 | 不劣于 v0.3.2 基线（README 实测 121–291 秒） |
| 反馈回流周期 | 上报时间戳 → 对应规则包发布的时间差 P50 | 无需改规则的上报单列 | 目标值·待基线确认 |

> 说明：以上均为**口径定义**，不是承诺值。当前无埋点，建议 2.0.0 先落地最小埋点跑一个版本，2.0.1 再据真实分布设定阈值。凡本文出现的非仓库数字，均按此规则标注。

## 4.2 三个候选方案对比

| 维度 | 方案 A · 渐进增强 | **方案 B · 规则平台化（推荐）** | 方案 C · 移动端原生化 |
|---|---|---|---|
| 思路 | 继续加机型脚本，补自动更新、报告页、回滚 | 规则 DSL + 规则包 + 签名校验 + 兼容层，把 37 份脚本迁成数据；Client 2.0 三步流程；诊断回流 | 做 Android App，用无线调试 / Shizuku 脱离电脑 |
| 实现成本 | 低 | 中高 | 高 |
| 开发复杂度 | 低 | 中（复用 `adapt.py` / `plan_switches` / 事件通道） | 高（权限模型、各 ROM 兼容、后台限制） |
| 用户体验 | 中（路径不变） | 好（3 步 + 可解释 + 可持续） | 很好（免电脑） |
| 风险 | 低 | 中（迁移期行为漂移，可用对拍回归兜住） | 高（触碰「adb 连接」「不 root」边界，需重新论证；且原生鸿蒙 / HDC 仍不支持） |
| 上线时间 | 快 | 中 | 慢 |
| 对八个矛盾的覆盖 | 2/8 | **8/8** | 4/8 |

**推荐 B，理由三条**：① 它直接消解 G-01/G-02/G-06 三个根因，而不是继续堆脚本；② 迁移风险可控——现有 `tests/` 100 个回归 + `adapt.py check_draft` + `compare_*` 对拍工具（`tests/compare_api.py` / `compare_phone_state.py`）足以做「行为逐字不变」断言，上游 ADR-0002/0005/0008 的重构正是这么做的；③ 不触碰七条硬边界，无需合规重审。

**不选 A**：成本最低但 G-01/G-02 会继续恶化，2.0 会退化成 0.4。**不选 C 作为 2.0**：它改变「仅支持 adb 连接的设备」这一明示边界，且 Android 后台限制与无线调试稳定性需要独立真机验证体系，应作为 **3.0 单独立项**（见演进路径）。

**演进路径（本期 → 后续 + 触发条件）**：
`2.0.0`（B 的 MVP：规则包 + 三步 + 变更清单 + 自动更新）→ `2.1.0`（诊断回流 + 增量守护 + 质量看板；触发条件：2.0.0 埋点数据可用）→ `2.2.0`（AI 辅助定位，可选；触发条件：跨语言 / 图标定位失败率经埋点确认高于阈值）→ `3.0`（移动端 / 免电脑；触发条件：边界评审通过 + 独立真机验证体系就绪）。

## 4.3 范围声明（做什么 / 不做什么）

**2.0 包含**：规则 DSL 与规则包、37 份脚本迁移工具与兼容层、三步流程、变更清单与单条回滚、只读体检报告、客户端自动更新、通知策略可配置、最小埋点与指标口径、备份加密与规则签名、诊断回流 MVP。

| 不做 | 理由 |

# 第六部分　核心模块详细方案

> 统一约定：功能需求编号 `FR-xx`；状态词「必须 / 应该 / 可以 / 禁止」；验收用 Given / When / Then；所有「目标值」均为待基线确认的建议值。

## 6.1 M-02　声明式规则引擎与规则包（最高优先）

**现状 → 目标**：37 份 `recipe.py` 把 Activity、文案、坐标、开关名写成 Python；`BUILD` 与 `--ref` 已具备版本匹配 / 安全模式的雏形。目标是把它升级为**可下发、可校验、可灰度、可回滚的数据**，同时保留现有 `Phone` 引擎作为执行器，**不重写读屏与拨动逻辑**。

**方案取舍**：

| 子方案 | 思路 | 取舍 |
|---|---|---|
| 2A 全量重写引擎 | 新规则 VM 替代 `fast.py` | 否决：丢弃大量 Issue 磨出来的防误点逻辑，风险不可控 |
| **2B 规则数据 + 兼容执行层（推荐）** | 规则包描述「去哪一页 / 找什么 / 拨哪个 / 保留什么」，由适配层翻译成现有 `Phone.start/go/tab/off/setting` 调用 | 复用 100% 引擎能力，迁移可对拍验证 |
| 2C 仅把词表外置 | 只改 `channel_policy.py` | 不解决 G-01，只是局部优化 |

**规则包（RulePack） Schema 建议字段**：`pack_id`、`schema_version`、`brand`、`models[]`、`build_patterns[]`（替代 `BUILD` 前缀比对）、`segments[]` → 每段含 `entry`（scheme / Activity / 底栏标签 / 图标判据）、`targets[]`（文案 / 繁体变体 / resource-id 短名 / 坐标百分比）、`keep[]`、`protected[]`、`confirm_policy`、`fallback: safe_mode`、`evidence`（来源 Issue / 真机记录）、`signature`、`expires`。**禁止**在规则包里放任何可执行代码。

| 编号 | 需求描述 | 业务规则 | 验收标准 |
|---|---|---|---|
| FR-01 | 规则包加载与签名校验 | 签名不符 / schema 版本不支持 / 已过期 → **必须**拒绝加载并回退本地内置只读规则，禁止静默降级执行 | Given 签名被篡改的规则包，When 客户端启动加载，Then 拒绝加载、提示「规则包校验未通过，已使用内置规则」且不执行任何点击 |
| FR-02 | 版本匹配与降级 | 沿用 `BUILD` 前缀比对；不匹配 → 自动 `--ref` 安全模式，**禁止**猜测性点击 | Given 设备系统版本与规则包 `build_patterns` 不符，When 生成执行计划，Then 该段标记为 `safe_mode` 且计划中不含任何非点名开关 |
| FR-03 | 37 份脚本迁移与对拍 | 提供迁移工具 `rulepack migrate`，产出草案后逐份用现有 `tests/compare_*` 对拍 | Given 任一历史脚本，When 用同版本规则包在录制 fixture 上执行，Then 步骤序列、点击坐标集合、回读结果与旧脚本逐项一致，差异必须为 0 |
| FR-04 | 灰度与回滚 | 规则包按 `pack_id + version` 灰度（建议 5% → 20% → 100%，目标值·待确认）；**必须**支持一键回退上一版本 | Given 灰度中规则包命中率低于阈值，When 触发回滚，Then 客户端下一次启动加载上一稳定版本并保留回滚记录 |

## 6.8 M-10　AI 辅助定位（可选，按 AI 需求六模块约束）

针对 G-01 中最难的一类是**跨语言 / 纯图标 / 改版页面**（README 已记录俄区 HyperOS 因「界面是俄语，引擎按中文找不到入口」而无专用脚本）。但 AI 引入必须严格受控，按 AI 功能专项补齐六模块：

| 模块 | 设计 |
|---|---|
| ① 任务定义 | 只做「页面语义定位」：给定当前页面骨架 + 目标开关语义，输出候选控件坐标与置信度；**不直接点击、不生成新规则、不改正式数据** |
| ② 输入契约 | 仅用现有脱敏页面骨架（层级 / 类型 / 百分比位置 / 标记，`docs/12:37-47`）；**禁止**输入截图原文、通知正文、账号页；缺关键字段时停止并转人工 |
| ③ 输出契约 | 结构化 `{candidates:[{node_id, xy, confidence, reason}]}`；必填置信度；低置信必须标注；结果可编辑、可拒绝 |
| ④ 质量验收 | 评测集覆盖常见 / 繁体 / 英文 / 俄文 / 纯图标 / 改版 / 拒答七类；阈值「目标值·待基线确认」（建议事实准确率 ≥85%、人工评审通过率 ≥90%）；**误关率 0** 为硬底线 |
| ⑤ 异常降级 | 置信度低 / 多源冲突 / 服务失败 / 触发高风险规则 → 一律降级为「显示原始页面骨架 + 请人工指认」，**禁止**统一报「系统繁忙」，更禁止猜测点击 |
| ⑥ 反馈闭环 | 记录被采纳 / 被拒绝的候选、最终人工选择，关联模型版本 + 提示版本 + 规则包版本，可复现 |

**AI 行为约束三层**：`Always do`（输出候选与置信度、保留人工确认）；`Ask first`（任何点击前必须人工确认，含高置信）；`Never do`（不得绕过受保护渠道、不得在安全模式下猜测、不得上传页面文字、不得自动发布规则）。

**方案取舍**：端侧小模型优先（离线、隐私）；云端模型作为可选且**默认关闭**；无论哪种，AI 结果都只是「给 `Phone.find` 的候选」，最终仍走现有 `plan_switches()` 与回读——**AI 不获得执行权**。

## 7.1 设计体系

| **C5 完成 / 变更清单** | 结果可解释、可单条撤销 | 顶部结果总览（成功 / 未确认 / 失败 / 跳过 / 已停止 五态计数）；中部变更清单表（每条含状态、前后值、单条撤销）；失败项右侧「重试此项」；底部「关闭开发者模式」卡 + 「重新检测这台手机」（`retry()`）| 空：无变更；载：账本读取；错：账本损坏时回退到日志视图；界：导出脱敏报告 | 结果计数 400ms 数字滚动；单条撤销成功后该行 180ms 淡出并刷新总览；「重试此项」只重跑该行；失败项用红色左描边但**不用**红色整块背景（避免制造焦虑） |
| **C6 还原中心** | 精确、不串台 | 三类粗粒度还原（快应用 / 广告组件 / 营销通知）+ 按批次筛选的单条撤销 + 还原预览（列明将影响哪些条目、来自哪台设备） | 空：无备份；载：备份读取；错：型号不匹配 / 备份损坏时**禁止**执行并说明；界：跨设备备份明确标注「属于另一台设备」 | 预览弹窗 180ms 淡入；执行中按钮转圈；完成后逐条回读状态以 120ms 间隔依次点亮 |
| **C7 规则中心** | 让「规则可更新」被感知 | 当前规则包版本 / 签名状态 / 更新时间 / 适用机型；更新日志折叠；灰度开关（高级）；「贡献新机型」入口 | 空：仅内置基线包；载：检查更新；错：签名不符红色告警且自动回退；界：多规则包按品牌分组 | 更新可用时卡片顶部 220ms 下滑提示条；更新完成后版本号 150ms 交叉淡入 |
| **C8 设置中心** | 把控制权交还用户 | 分组：连接（adb 路径，沿用现有 `set_adb_path`）、更新（自动检查 / 规则包自动更新）、外观（语言 / 主题 / 动效）、隐私与上报（上报开关、留存说明、查看将发送什么）、无障碍（键盘 / 读屏 / 对比度）、关于（版本、署名、许可证、硬边界说明） | 每组的空 / 载 / 错 / 界态独立；任何涉及数据上送的开关**默认关闭或保持现状**，切换时展示「将发送什么」预览 | 分组折叠 180ms；开关沿 `--knob / --on / --off` 既有令牌做 150ms 滑块过渡；危险设置（关闭校验）需二次确认 |

## 8.2 埋点与指标口径

**事件清单**（本地优先存储，上报沿用现有脱敏通道，用户可关闭）：`device_connected`、`scan_started/completed`、`plan_previewed/confirmed`、`job_started/finished`、`step_finished`、`switch_changed`、`channel_changed`、`rollback_performed`、`rulepack_updated`、`report_submitted`、`update_applied`。

**公共字段**：匿名安装编号（复用现有 `install-id`，不含设备标识）、客户端版本、规则包版本、品牌 + 型号族 + 系统大版本（**完整型号不上传**）、批次 ID、结果码、耗时、规则 ID。**禁止**采集应用列表、通知内容、账号信息、截图、IP 原文、序列号。

| 指标 | 公式 | 排除项与歧义 |
|---|---|---|
| 治理完成率 | 完成页「全部成功」批次 ÷ 启动批次 | 排除主动停止、检测退出；APP_DENIED 不计失败 |
| 回读确认率 | 回读确认目标态条目 ÷ 计划拨动条目 | 排除 `kept` / 灰态 `disabled` / 扫描排除 / 前台服务渠道；「未确认」单独统计，不算成功也不算失败 |
| 误关率 | 受保护或服务类条目发生状态变化数 ÷ 总拨动数 | **无排除项，底线 0**，触发即阻断发布 |
| 规则命中率 | 成功定位并执行条目 ÷ 适用条目 | 安全模式降级段落单列，不混入分母 |
| 规则覆盖率 | 有专用且 `BUILD` 匹配的规则包机型 ÷ 检测机型 | 仅参考规则 / 安全模式机型单列 |
| 执行耗时 P95 | 批次开始→结束耗时 P95 | 暂停等待用户时间单列 |
| 反馈回流周期 | 上报时间→对应规则包发布时间 P50 | 无需改规则的上报单列 |

> 复用既有通道：引擎已有「事件行 / 载荷行」前缀机制（`CONTEXT.md:79-81`），埋点应作为**新的载荷类型**接入，不新增日志格式、不污染界面日志与步骤摘要 `tail`。

## 8.3 权限与安全要求

| 角色 | 功能权限 | 数据权限 |
|---|---|---|
| 终端用户 | 体检、治理、单条撤销、导出脱敏报告、关闭上报 | 仅本机、仅本设备序列号的账本与备份 |
| 规则贡献者 | 提交 RulePack 草案 | 仅自己提交的草案；不可发布 |
| 规则审核 / 发布者 | 审核、签名、灰度、回滚 | 全局规则包（不含任何用户数据） |
| 上报服务账号 | 仅写入新报告（沿用 `docs/12:59` 低权限账号） | 只读聚合统计，不读取单条原文 |

**禁止**：新增任何系统权限申请；规则包内含可执行代码；AI 直接获得点击执行权；静默自动更新 / 静默规则下发；跨设备读取备份。

## 8.4 异常处理清单

| 场景 | 表现 | 处理方式 |
|---|---|---|
| 规则包签名不符 / 过期 / schema 不支持 | 启动加载失败 | 拒绝加载、回退内置只读规则、明确提示（FR-01） |
| 版本不匹配 | 段落大量「没找到」 | 自动降级安全模式，禁止猜测点击（FR-02） |
| 断线（已确认） | 后续步骤无意义 | 后续步骤一次性标记跳过，提示重连后「继续」（沿用 `Dispatcher._work:859-866`） |
| 读屏被占用 / 锁屏 | `ui_busy` / `locked` 事件 | 提示排查步骤，后续读屏任务跳过，不自动停用无障碍服务（`docs/08:251`） |
| 折叠屏展开 | 坐标错位 | 提示「合上用外屏」，不自动跑机型脚本 |
| 无候选渠道 | 扫描结果为空 | 区分「无候选」与「扫描失败」（FR-16） |
| APP_DENIED | 应用通知整体关闭 | 记为豁免，不算失败（`CONTEXT.md:127`） |
| 备份损坏 / 型号不匹配 | 还原风险 | **禁止执行**，说明原因（`3f5089d` 教训） |
| 回滚冲突 | 当前态与账本不符 | 先回读，冲突则拒绝并提示人工确认（FR-12） |
| 自动更新失败 / Windows SmartScreen / MOTW | 安装受阻 | 保留旧版本可用，给出手动下载与「解除锁定」指引（`docs/08:28-29`） |
| AI 低置信 / 服务失败 | 无法定位 | 降级为「页面骨架 + 人工指认」，禁止猜测点击（6.8 节） |
| 上报限频 | 3 次/小时 | 沿用现有提示，不阻塞主流程 |

## 9.3 灰度与回滚

- 规则包：按 `pack_id + version` 灰度 5% → 20% → 100%（比例为目标值·待确认），命中率 / 误关率任一触线即回退上一稳定包（FR-04）。
- 客户端：自动更新分批推送，保留旧版本可启动；更新失败不破坏现有备份与账本。
- 数据迁移：从 `backups/` 旧格式生成账本时**只增不删**，旧文件保留只读一份；迁移前后记录数一致、关键字段抽样比对一致、差异必须为 0（沿用存量迁移方案模板）。
- 上线后验证：每版本至少 1 个核心指标看板；`waiting-for-verify` 的规则包必须经报告者真机确认才转为「已验证」。
